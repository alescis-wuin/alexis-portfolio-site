Plateforme de streaming vidéo

Finalisé

Streamfolio

Plateforme de streaming full-stack : catalogue, sécurité, administration média et pipeline MP4/HLS avec FFmpeg.

Objectif
Concevoir une plateforme vidéo full-stack avec un pipeline média persistant.
Démonstration
Sécurité, streaming, traitements asynchrones, stockage objet, tests et CI.
Domaines
Backend Full-stack Données DevOps

Problème

Ce que le projet cherche à résoudre

Réunir accès sécurisé, expérience de lecture vidéo, administration des médias et traitements FFmpeg sans lier les opérations longues au cycle de vie des requêtes HTTP.

Rôle

Mon rôle

Conception et développement de bout en bout : architecture Spring Boot, sécurité, streaming, administration média, persistance, pipeline FFmpeg, tests et environnement Docker.

Stack

Java Spring Boot PostgreSQL Redis MinIO Docker HLS Playwright

Architecture

Comment le système est structuré

  • Spring Boot porte le catalogue, l’authentification, l’administration et les endpoints de streaming.
  • PostgreSQL/Flyway stockent les données métier, Redis les sessions et MinIO les médias.
  • Les traitements FFmpeg passent par des jobs persistés et des workers bornés.

Décisions

Décisions techniques

  • Persister les jobs média. Les traitements longs survivent aux redémarrages et peuvent être relancés ou annulés sans dépendre d’une requête HTTP.
  • Séparer les stockages. PostgreSQL conserve les données métier, Redis les sessions et MinIO les objets média.

Schéma

Vue d’ensemble de l’architecture

Le schéma complète l’étude de cas avec les composants et frontières réellement présents dans le projet.

Implémentation

Points techniques principaux

  • Authentification Spring Security avec BCrypt, cookies HttpOnly/SameSite et sessions Redis.
  • Catalogue, recherche, filtres, watchlist et progression de lecture.
  • Streaming MP4 avec HTTP Range, WebVTT et HLS via hls.js.
  • Administration média et upload avec validation des sources.
  • Jobs média persistés avec workers bornés, reprise après redémarrage, retry exponentiel et annulation FFmpeg.
  • PostgreSQL/Flyway, MinIO, Docker et tests Playwright.

Difficultés

Difficultés résolues

  • Servir des médias volumineux. MP4 progressif, HTTP Range et HLS couvrent plusieurs modes de lecture.
  • Fiabiliser le pipeline. Persistance, reprise et annulation rendent les traitements longs observables et contrôlables.

Qualité

Tests et garde-fous

  • Tests Maven sur sécurité, streaming et administration.
  • Smoke tests et E2E Playwright.

Livraison

Livraison et CI/CD

  • Docker Compose fournit PostgreSQL, Redis et MinIO.
  • GitHub Actions relance la validation du dépôt.

Résultats

Résultats observables

  • Parcours cohérent de l’administration jusqu’à la lecture vidéo.
  • Pipeline média capable de reprendre des traitements persistés.

Compromis

Compromis techniques

  • FFmpeg reste local et le projet ne simule pas une ferme de transcodage distribuée.
  • Redis et MinIO sont utilisés dans un environnement de démonstration mono-site.

Limites

Limites assumées

  • Pas de DRM ni de CDN global.
  • Redis reste mono-nœud.
  • Le transcodage n’est pas distribué.

Suite

Prochaines étapes

  • Compléter l’observabilité et les essais de charge avant toute ambition de service public.

Preuve de compétence

Ce que ce projet démontre

  • Le pipeline média est persistant et séparé des requêtes HTTP.
  • Les responsabilités de données métier, sessions et stockage média sont séparées.
  • Les limites de production — DRM, CDN, haute disponibilité et transcodage distribué — sont documentées.
