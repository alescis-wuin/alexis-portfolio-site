Application météo desktop · Prototype

Aelia

Application météo JavaFX avec fournisseur simulé, données météo/air/UV/pollen, thème sombre, contraste renforcé et contrôles clavier.

Desktop Accessibilité Architecture
Voir le dépôt GitHub Télécharger le CV

Problème

Ce que le projet cherche à résoudre

Préparer une application desktop extensible autour de fournisseurs météo, en conservant testabilité, accessibilité et séparation des ports/adaptateurs.

Rôle

Mon rôle

Conception d’un prototype météo desktop JavaFX : architecture orientée fournisseur, composants UI, accessibilité, données typées, tests et documentation itérative.

Stack

Java Java 21 JavaFX AtlantaFX Maven Tests GitHub Actions

Architecture

Comment le système est structuré

  • Interface JavaFX/AtlantaFX découpée autour de vues et composants dédiés au tableau de bord météo.
  • Port orienté fournisseur permettant de substituer le provider local simulé par des intégrations distantes.
  • Modèles météo typés, avec formatage des valeurs conservé dans la couche UI.
  • Exécution JavaFX classpath-based volontairement non modulaire pendant l’évolution rapide des composants.

Décisions

Décisions techniques

  • Commencer par un provider déterministe. Le fournisseur simulé stabilise l’interface et les tests pendant que le contrat destiné aux futures API distantes évolue.
  • Conserver les valeurs typées jusqu’à la présentation. Les données temporelles et physiques ne sont pas stockées uniquement sous forme de chaînes ; le formatage est repoussé vers l’UI.
  • Prioriser l’accessibilité du prototype. Navigation clavier, tooltips, contrastes et métadonnées d’accessibilité sont intégrés avant même le branchement à une API distante.
  • Rester temporairement en classpath. Le lancement non modulaire simplifie Maven et IntelliJ tant que l’interface évolue fortement, au prix d’une frontière de modules moins stricte.

Schéma

Vue d’ensemble de l’architecture

Le schéma complète l’étude de cas avec les composants et frontières réellement présents dans le projet.

Implémentation

Points techniques principaux

  • Structure JavaFX MVC avec port orienté fournisseur.
  • Fournisseur local simulé pour météo, qualité de l’air, UV et pollen.
  • Requêtes de valeurs courantes et abonnements live configurables.
  • Tables de limites API et de données supportées.
  • Contrôles compatibles clavier, tooltips et métadonnées d’accessibilité JavaFX.
  • Build Maven, tests unitaires et workflow GitHub Actions.

Difficultés

Difficultés résolues

  • Garder les indicateurs cohérents avec les données. Les jauges et cartes ont été progressivement détachées de progressions codées en dur pour dériver leur état de valeurs météo typées.
  • Rendre un dashboard dense utilisable au clavier. Les contrôles doivent rester accessibles sans souris malgré le nombre de cartes, sélecteurs et indicateurs affichés.
  • Préparer les API sans déstabiliser l’UI. Le contrat de provider permet de faire évoluer les sources de données sans réécrire les composants visuels.

Qualité

Tests et garde-fous

  • Commandes Maven test et verify documentées pour la validation locale.
  • Tests unitaires autour des modèles, providers et comportements principaux.
  • Workflow GitHub Actions présent pour vérifier le build du projet.

Livraison

Livraison et CI/CD

  • Lancement reproductible via mvn javafx:run.
  • Import optionnel des polices Luciole et Hack via Makefile, avec fallback système lorsque les fichiers ne sont pas présents.
  • Documentation versionnée décrivant architecture, accessibilité, UI/UX et corrections successives.

Résultats

Résultats observables

  • Un dashboard météo desktop visuellement abouti malgré son statut de prototype.
  • Une base prête à recevoir des fournisseurs distants sans lier directement l’UI à une API particulière.
  • Une prise en compte de l’accessibilité et du clavier dès les premières itérations.

Compromis

Compromis techniques

  • Le provider simulé garantit des scénarios reproductibles mais ne démontre pas encore la résilience face à une API météo réelle.
  • Le runtime classpath réduit la complexité de configuration mais reporte l’éventuel durcissement du module system.
  • Le projet privilégie la qualité de lecture et l’accessibilité à une intégration immédiate d’un grand nombre de fournisseurs.

Limites

Limites assumées

  • Le provider principal reste simulé et aucune API météo distante n’est appelée dans l’état actuel.
  • Le projet demeure un prototype et ne couvre pas encore les pannes, quotas ou variations de schéma d’un fournisseur externe.
  • Le lancement non modulaire est assumé comme décision transitoire.

Suite

Prochaines étapes

  • Implémenter au moins un adaptateur météo distant derrière le contrat existant.
  • Ajouter des tests d’intégration autour des erreurs réseau, quotas et données partielles.
  • Réévaluer le passage au module system lorsque la structure de l’interface sera suffisamment stabilisée.
